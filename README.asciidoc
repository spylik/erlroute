= Erlroute

Erlroute is a pub/sub routing library for Erlang/OTP. Publishers emit messages tagged with a topic and the calling module; subscribers register destinations that receive those messages. The routing table lives in ETS so the hot path (cached routes) is a single ETS lookup with no gen_server round-trip.

== Quick start

[source,erlang]
----
%% Subscribe the current process to all messages from module my_producer
erlroute:sub(my_producer).

%% Subscribe to a specific topic from any module
erlroute:sub(<<"sensor.temperature">>).

%% Publish from inside my_producer — routing is a single ETS read after the first call
erlroute:pub(?MODULE, self(), ?LINE, <<"sensor.temperature">>, Reading).
----

== Topics and source matching

A topic is any binary string. A subscriber can filter by topic, by the publishing module, or both:

[source,erlang]
----
%% Any module, specific topic
erlroute:sub(<<"sensor.temperature">>, self()).

%% Specific module, any topic (wildcard <<"#">>)
erlroute:sub(my_producer, self()).

%% Both — specific module + specific topic
erlroute:sub([{module, my_producer}, {topic, <<"sensor.temperature">>}], self()).
----

The wildcard topic `<<"#">>` matches all published topics. It is the implicit topic when you subscribe to a module by atom.

== Delivery destinations

=== Process (pid or registered name)

[source,erlang]
----
%% Current process, default `info` delivery (plain message send)
erlroute:sub(<<"events">>, self()).

%% Registered name, cast delivery
erlroute:sub(<<"events">>, {process, my_worker, cast}).

%% Registered name, call delivery (blocks the pub call)
erlroute:sub(<<"events">>, {process, my_worker, call}).
----

=== Anonymous function

The function receives the payload only (arity 1) or topic + payload (arity 2):

[source,erlang]
----
erlroute:sub(<<"events">>, fun(Payload) -> ... end).
erlroute:sub(<<"events">>, fun(Topic, Payload) -> ... end).
----

=== Static MFA

[source,erlang]
----
%% Calls my_handler:on_event(Payload, ExtraArg) on publish
erlroute:sub(<<"events">>, {my_handler, on_event, [ExtraArg]}).
----

=== Function or MFA on a remote node

[source,erlang]
----
erlroute:sub(<<"events">>, {remote_node@host, fun(P) -> ... end}).
erlroute:sub(<<"events">>, {remote_node@host, {my_handler, on_event, []}}).
----

== Unsubscribe

[source,erlang]
----
erlroute:unsub(<<"events">>, self()).
erlroute:unsub(my_producer, self()).
----

Process subscriptions added via pid are cleaned up automatically when the process dies.

== Publish modes

[cols="1,3"]
|===
| Mode | Behaviour

| `sync`
| Delivers to all known subscribers before returning. Returns `[{Dest, Method}]`.

| `async`
| Spawns a process to handle delivery; returns `[]` immediately.

| `hybrid`
| Delivers synchronously to cached routes (the common case), then spawns a process to handle any uncached subscribers discovered in `?SUBETS` or remote routes. Returns the set of destinations hit synchronously.
|===

The default via parse transform is `hybrid`. Explicit call:

[source,erlang]
----
erlroute:pub(?MODULE, self(), ?LINE, <<"events">>, Payload, sync,  erlroute:cache_table(?MODULE)).
erlroute:pub(?MODULE, self(), ?LINE, <<"events">>, Payload, async, erlroute:cache_table(?MODULE)).
erlroute:pub(?MODULE, self(), ?LINE, <<"events">>, Payload, hybrid,erlroute:cache_table(?MODULE)).
----

== Parse transform

Add to your module's compile options:

[source,erlang]
----
-compile({parse_transform, erlroute_transform}).
----

The transform rewrites `erlroute:pub` calls at compile time to embed the ETS cache table name as a literal atom and fill in `?MODULE`, `self()`, and `?LINE` automatically, eliminating all runtime overhead on the hot path:

[source,erlang]
----
%% With parse transform — all args resolved at compile time
erlroute:pub(<<"sensor.temperature">>, Reading).
erlroute:pub(<<"sensor.temperature">>, Reading, sync).
----

Without parse transform, use the full form or the `?PUB` macros from `erlroute.hrl`.

== Distributed Erlang

Erlroute works transparently in a distributed cluster:

* When a node subscribes to a topic, the subscription is propagated to all connected nodes via a one-time sync followed by incremental updates on change.
* On publish, cross-node routes are dispatched via the router pool on the receiving node (`erlroute_router`), which fans out to local subscribers only — avoiding re-forward storms.
* On node disconnect, all routes to that node are removed. On reconnect, a full sync restores them automatically.
* Cross-node delivery supports process and poolboy destinations (the remote process or pool receives the message directly).

== ETS caching and performance

On the first publish to a `{Module, Topic}` pair, erlroute walks `?SUBETS` and any remote routes to build the delivery list, then writes `#cached_route` entries into a per-module ETS table. Subsequent publishes to the same topic hit this cache directly — no gen_server call, no ETS bag scan.

Cache entries are invalidated automatically when:
* a subscriber unsubscribes;
* a subscribed process dies;
* a remote route changes (node reconnects with a different router assignment).

== When not to use erlroute

* You need to exchange messages with non-Erlang services — use an AMQP broker or similar.
* You need durable queues, persistence, or at-least-once delivery — erlroute is in-memory only.
* You need content-based routing on message fields — erlroute routes on topic + module only.
