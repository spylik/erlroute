= Erlroute

Erlroute is a pub/sub routing library for Erlang/OTP. Publishers emit messages tagged with a binary topic; subscribers register local or remote destinations that receive those messages. The subscription table lives in ETS so the hot publish path is a single ETS lookup with no gen_server round-trip.

== Quick start

[source,erlang]
----
%% Subscribe the current process (info delivery)
erlroute:sub(<<"sensor.temperature">>).

%% Publish
erlroute:pub(<<"sensor.temperature">>, Reading).
----

== Subscribe

`sub/1` subscribes the calling process with default `info` (plain send) delivery.
`sub/2` accepts a destination as the second argument.

=== Process (pid or registered name)

[source,erlang]
----
%% Current process, info delivery
erlroute:sub(<<"events">>).
erlroute:sub(<<"events">>, self()).

%% Registered name, info delivery
erlroute:sub(<<"events">>, my_worker).

%% Registered name, cast delivery
erlroute:sub(<<"events">>, {process, my_worker, cast}).

%% Registered name, call delivery
erlroute:sub(<<"events">>, {process, my_worker, call}).
----

=== Anonymous function

The function receives the payload only (arity 1) or topic + payload (arity 2).
Delivery is always `cast` (spawned):

[source,erlang]
----
erlroute:sub(<<"events">>, fun(Payload) -> ... end).
erlroute:sub(<<"events">>, fun(Topic, Payload) -> ... end).
----

=== Static MFA

[source,erlang]
----
%% Calls my_handler:on_event(Payload, ExtraArg)
erlroute:sub(<<"events">>, {my_handler, on_event, [ExtraArg]}).
----

Erlroute checks the function's arity at subscribe time and automatically prepends `Topic` when the function accepts it (arity `length(Args) + 2` vs `length(Args) + 1`).

=== Function or MFA on a remote node

[source,erlang]
----
erlroute:sub(<<"events">>, {remote_node@host, fun(P) -> ... end}).
erlroute:sub(<<"events">>, {remote_node@host, {my_handler, on_event, []}}).
----

== Unsubscribe

[source,erlang]
----
%% Unsubscribes self() with info delivery (and registered name if the process has one)
erlroute:unsub(<<"events">>).

%% Unsubscribe a specific destination — same shape as sub/2
erlroute:unsub(<<"events">>, my_worker).
erlroute:unsub(<<"events">>, {process, my_worker, cast}).
erlroute:unsub(<<"events">>, fun(P) -> ... end).

%% Bulk unsubscribe — remove a process from *every* topic at once
erlroute:unsub(all).                %% the calling process (by pid and registered name)
erlroute:unsub(all, my_worker).     %% a given process: pid or registered name
----

`unsub/1` removes both the pid-based and name-based subscriptions for the calling process. Pid subscriptions are also cleaned up automatically when the subscribed process exits.

Passing the atom `all` unsubscribes a process from every topic it is subscribed to. `unsub(all)` targets the calling process; `unsub(all, Dest)` targets a given process destination (a pid or a registered name). Removals propagate to other nodes just like a single-topic `unsub`. Bulk unsubscribe applies to process destinations only — function/MFA subscriptions are not removed this way.

== Publish

[source,erlang]
----
%% Sync — delivers to all subscribers, returns [{Dest, Method}]
erlroute:pub(<<"events">>, Payload).
erlroute:pub(<<"events">>, Payload, sync).

%% Async — spawns delivery, returns [] immediately
erlroute:pub(<<"events">>, Payload, async).

%% Local only — skips cross-node delivery
erlroute:pub_local(<<"events">>, Payload).
----

[cols="1,3"]
|===
| Mode | Behaviour

| `sync` (default)
| Delivers to all local subscribers and dispatches to remote router pool before returning. Returns `[{Dest, Method}]` for each local delivery made.

| `async`
| Spawns a process for delivery; returns `[]` immediately. The router pool also spawns delivery on the remote side, avoiding head-of-line blocking.
|===

== Distributed Erlang

Erlroute works transparently across a distributed cluster:

* When a node's subscriber set for a topic changes, the delivery descriptor (`direct` for a single process subscriber, `pool` otherwise) is propagated to all connected nodes as an incremental update.
* On publish, cross-node routes are dispatched via a sticky router pool on the receiving node. Each topic is assigned to one router at first publish and the assignment is stable until the router dies.
* `pub/2,3` dispatch to all nodes; `pub_local/2` is local-only and is the function called by the remote router after receiving a cross-node message.
* On node disconnect, all routes to that node are removed. On reconnect, a full sync restores them.

=== Router pool

Each node runs a fixed pool of router processes (`erlroute_router`). Topics are assigned to routers round-robin on first publish and the assignment is stored in ETS. For `async` publishes the router spawns delivery to avoid head-of-line blocking from slow `call` subscribers on one topic stalling other topics sharing the same router.

Pool size defaults to 10 and is configurable:

[source,erlang]
----
{erlroute, [{router_pool_size, 20}]}
----

== Performance notes

* The publish hot path is one `ets:lookup` on `?SUBETS` (keyed by topic) plus one `ets:lookup` on `?REMOTETS` when cross-node routes exist. No gen_server call on the publish path.
* Subscriptions are stored as `{topic(), [sub_spec()]}` in a set table. A separate bag table (`?PIDETS`) maps each subscribed pid to its topics, making process-exit cleanup O(topics-subscribed-by-that-pid) rather than O(total-topics).
* `call` delivery (blocking gen_server:call) blocks the publishing process for the duration on the local path. Avoid for high-throughput topics or use `async` pub type.

== When not to use erlroute

* You need to exchange messages with non-Erlang services — use an AMQP broker or similar.
* You need durable queues, persistence, or at-least-once delivery — erlroute is in-memory only.
* You need content-based routing on message fields — erlroute routes on topic only.
